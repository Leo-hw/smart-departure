# T-018 리포트 — 대중교통 이동 시간 변동 정책

## AC 결과

- ✅ 폰 로그의 동일 일정에서 17:35 요청 시 50분/18:00 출발, 17:40에 45분/18:05, 17:45에 47분/18:03, 17:50에 50분/18:00, 18:20에 55분/17:55가 기록됐다. 일정 ID·이름·장소는 기록하지 않는다.
- ✅ 정상 API 응답의 이동 시간이 늘 때만 출발 시각을 앞당기는 보수적 정책을 선택했다. 고정 `departureTime`은 시간이 흐르면 목표 출발이 과거가 되고, 최초값 고정은 급증을 반영하지 못한다. [Google Routes 문서](https://developers.google.com/maps/documentation/routes/transit-route)에 따르면 시간 미지정 시 요청 시각 기준이며, 미래 대중교통 예측도 일관성이 보장되지는 않는다.
- ✅ 일정 시작 시각·장소·이동수단·provider가 바뀌면 기준을 재설정한다. 캐시·추정값은 정상 API 기준을 높이지 않고, 처음이 캐시·추정값이면 다음 정상 API 응답으로 교체한다. 급증 시 일정 시작 전까지 출발 catch-up을 허용한다.
- ✅ 로컬 단위 테스트 68개, `py_compile`, `git diff --check` 통과. Maps fallback 및 dedup 회귀 테스트도 통과했다.

## 운영 검증

- 변경 전 폰 로그에서 같은 경로의 출발 시각이 최대 10분 이상 흔들리는 것을 재확인했다. 이것은 관찰 사실이며 원인이 다음 차 시각 변화인지는 확정하지 않았다.
- 변경 후 실제 일정의 알림 도착·시각 안정성은 별도 관찰이 필요하다. 배포 후 폰 코드 반영과 단위 테스트·타이머 실행을 스모크 검사한다.

## 기획 대비 변경

- 별도 상태 파일 대신 기존 `schedule_today.json`에 정상 API의 최대 이동 시간을 저장한다. 이전 버전 스냅샷은 재사용하지 않는다.
- 현재 재계산값보다 과거 정상 API 최대값을 사용하면 알림의 이동 시간은 보수적 추정으로 표기된다.

## 이슈 및 인계

- 최초 조회가 이미 과대 추정이면 출발 알림이 일찍 올 수 있다. 정책은 지각 위험보다 조기 알림을 우선한다.
- 캘린더가 한 틱 동안 일정을 반환하지 않아 스냅샷에서 사라진 뒤 다시 나타나면 기준을 새로 만든다.
- T-016 카카오 전환 시에도 이 정책이 적용되려면 provider별 응답의 `source` 구분을 유지해야 한다.
